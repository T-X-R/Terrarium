# Terrarium

*Where Software Learns to Grow Itself*

## 一、背景

当前主流的 AI 开发范式，通常是“人提出需求，AI 作为外部代理去修改项目”。在这种模式下，AI 更像一个观察者、操作者或工程助手：它站在项目外部，读取代码、执行命令、编写功能、修复 bug，但项目本身仍然只是一个被动对象。

这种范式已经很有价值，但它仍然有明显边界：AI 只是“帮助开发项目”，而不是“项目本身拥有持续自我演化的能力”。

因此，一个更进一步的问题出现了：**能否把项目从静态产物，变成具备自我感知、自我判断、自我修改能力的动态生命体？**

换句话说，我们想探索的，不再是“AI 如何更好地开发软件”，而是：**软件项目能否拥有自己的认知核心，并像生命体一样持续生长与迭代。**

---

## 二、Terrarium 的理想愿景

Terrarium 的理想，并不是做另一个“更强的 AI 编程助手”，而是尝试构建一个让软件项目能够在边界之内自我生长的环境。

在这一设想中，AI 不再只是外部工具，而是逐渐成为项目内部的认知核心；项目的代码、页面、接口、数据、配置、测试与运行状态，则共同构成它的“身体”。

在这种设想下，项目能够像一个统一生命体一样运行：

- 当某个功能不好用时，它能感知到问题；
- 当某个页面不够美观时，它能识别并形成改进意图；
- 当测试失败、性能退化、结构混乱时，它能主动调整自己；
- 当某种尝试有效时，它能记住经验；
- 当某种行为越界时，它能被自身的边界系统约束。

因此，这种系统的核心不是“外部 agent 操作项目”，而是：

> **项目本身就是一个拥有 AI 大脑的生命体。**

Terrarium 想要提供的，正是这样一个“软件生态箱”：在这个环境中，项目并非一次性被构建完成，而是能够在目标、身份与边界之内，持续进行自我演化。

---

## 三、核心公式：Project Organism

为了抽象这种“项目即生命体”的架构，我们提出如下公式：

```text
Project Organism
= Perception
+ Cognition
+ Agency
+ Memory
+ Evaluation
+ Identity
+ Drives
+ Boundaries
+ Meta-Learning
```

这九个部分并不是简单的模块堆叠，而是一个自演化项目所需的九类核心能力：

### 1. Perception（感知）

项目对自身及环境的观测能力，包括代码状态、测试结果、日志、运行表现、视觉界面、用户行为等信号。

### 2. Cognition（认知）

项目对感知结果进行理解、解释和推理的能力，用于识别问题、分析原因，并形成候选迭代方向。

### 3. Agency（行动）

项目对自身进行实际修改的能力，例如改代码、调配置、重构模块、运行命令、回滚变更等。

### 4. Memory（记忆）

项目保留上下文、历史、经验与教训的能力，使其不只是重复尝试，而能真正积累成长。

### 5. Evaluation（评价）

项目判断“当前是否变得更好”的能力，用于评估功能正确性、稳定性、体验、美观性、一致性与整体质量。

### 6. Identity（身份）

项目对“我是谁、我想成为什么样的软件”的长期自我定义。它决定哪些变化符合自身定位，哪些变化偏离自身本质。

### 7. Drives（驱动）

项目内部推动变化发生的张力来源，例如对完整性、稳定性、美观性、一致性、性能、表达能力等的追求。

### 8. Boundaries（边界）

项目的底线与约束系统，用于防止越界、失控或无意义膨胀，保证其演化过程可控、可收敛。

### 9. Meta-Learning（元学习）

项目对“自己如何迭代”这件事进行再学习的能力，用于优化策略、修正偏差、总结模式，使其越来越会成长。

## 四、Lifecycle 机制：让能力真正活起来

仅仅拥有 Project Organism 的九项能力，还不足以让 Terrarium 成为一个真正持续生长的系统。原因在于：当前模型内核本质上仍然是被动的。若没有外部唤醒，它不会持续观察、反思或调整项目。

因此，Terrarium 还需要一层 **Lifecycle 机制**，负责把“潜在能力”转化为“持续活动”。

可以将其抽象为：

```text
Terrarium
= Project Organism
+ Lifecycle
```

其中，Lifecycle 负责项目的唤醒、节律、触发与休眠管理。它至少包含以下几个部分：

### 1. Heartbeat（心跳）

Heartbeat 是 Terrarium 的基础唤醒机制。它通过固定周期触发系统，使项目即使在没有外部命令的情况下，也能够定期检查自身状态。

Heartbeat 的意义不只是“定时 ping 一下”，而是让项目具备最基本的时间感与存在感。没有 Heartbeat，Terrarium 仍然只是一个被动响应的工具；有了 Heartbeat，它才开始接近一个具有持续活性的系统。

### 2. Event Triggers（事件触发）

除了定时心跳，Terrarium 也应当能被关键事件即时唤醒。例如：

- 测试失败
- 构建失败
- 页面崩溃
- 依赖变化
- 用户行为异常
- 新的外部反馈到来

这些事件触发更像神经反射，它们使系统能够对重要变化作出更及时的响应。

### 3. Sleep / Wake Policy（休眠与唤醒策略）

Terrarium 不应该在每一次唤醒后都强行执行大规模行动。更合理的方式是：每次醒来先判断“现在是否值得行动”，若没有显著变化或没有足够张力，则继续保持休眠或仅做轻量记录。

这意味着 Terrarium 的活性不是无节制的持续运转，而是一种有节律、有选择的活动状态切换。

### 4. Rhythm and Metabolism（节律与代谢）

从更生命体的角度看，Heartbeat 只是脉冲，而真正让系统长期维持活性的，是其节律与代谢机制。

Terrarium 可以具备不同层次的运行节律，例如：

- **快速心跳（如每 10 分钟）**：执行轻量巡检，查看是否有显著变化；
- **标准心跳（如每 30 分钟）**：执行一次完整的感知—认知—判断流程；
- **深度反思（如每 6 小时或每天）**：执行更高层次的总结、记忆整理与元学习。

通过这种分层节律，Terrarium 才能避免“为了活着而不停乱动”，而是在合适的时机做合适层级的事情。

### 5. Human Governance（人类治理）

尽管 Terrarium 追求自我生长，但人类仍然是愿景、价值和边界的设定者。因此，Lifecycle 机制中还需要保留人类治理接口，用于：

- 注入新的高层目标
- 调整边界条件
- 暂停或恢复演化
- 审批高风险变更

这保证了 Terrarium 不会脱离人的总体意图，而是在“自主演化”与“人类治理”之间保持平衡。

从整体上看，Lifecycle 机制的意义在于：

> **Project Organism 定义了 Terrarium 具备哪些能力，而 Lifecycle 决定这些能力如何持续发生。**

换句话说，没有 Lifecycle，Terrarium 只有器官；有了 Lifecycle，它才开始拥有活性。

---

## 五、这一公式的意义

Project Organism 与 Lifecycle 的意义，不在于把项目机械地拆成若干模块，而在于定义：**一个真正能够持续自我演化的软件，至少需要哪些存在性能力，以及这些能力如何被持续激活。**

它意味着我们对软件项目的理解正在发生变化：

- 软件不再只是被制造、被维护的对象；
- 软件开始拥有自我观察、自我解释、自我修正的可能；
- AI 不再只是外部工具，而成为软件内部的认知核心；
- 项目的演化，也不再只是 backlog 驱动，而是由感知、认知、驱动、评价、边界与生命周期共同塑造。

从这个角度看，Terrarium 并不是一个传统意义上的“开发框架”，而更像是一个**让软件生命体得以生长的环境与内核设想**。

## 六、基于 Skills 的设计设想

除了将 Terrarium 实现为一个庞大而封闭的系统，另一种更轻量、也更符合当前 AI 工程趋势的方案，是将其设计为：

> **少量内核代码 + 一组可插拔的认知/执行 Skills**

在这种设想下，Terrarium 不必一开始就成为一个“很重的平台”，而可以由一个轻量主循环协调多个能力型 Skills。内核只负责维持基本生命活动逻辑，而具体能力则通过 Skills 形式被按需调用。

一个可能的映射方式如下：

- **Perception Skill**：负责观测项目状态，如日志、测试、构建、运行时信息、文件结构等；
- **Vision Skill**：负责视觉观测，如网页截图、布局分析、界面质量判断；
- **Cognition Skill**：负责解释状态、分析问题、形成候选迭代方向；
- **Agency Skill**：负责执行修改，如编辑代码、运行命令、调整配置、重构模块；
- **Memory Skill**：负责记录上下文、经验、历史演化轨迹与教训；
- **Evaluation Skill**：负责判断改动后的结果是否更优；
- **Identity Skill**：负责维护项目的自我定义与风格一致性；
- **Boundary Skill**：负责检查是否越界、失控或偏离目标；
- **Meta-Learning Skill**：负责从多轮演化中总结规律，并调整未来策略；
- **Heartbeat / Lifecycle Skill**：负责定时唤醒、检查触发条件、决定轻巡检还是深度反思，并协调系统节律。

这种做法的优势在于：

1. **轻量化**：不必预先实现一个庞大全能系统，而是先实现最小内核；
2. **可插拔**：不同项目可以按需启用不同 Skills，例如网页项目更依赖 Vision Skill，而 CLI 项目则可能几乎不需要视觉能力；
3. **可演化**：随着项目复杂度上升，可以不断新增或替换 Skills，而不必推倒重来；
4. **更符合现有生态**：当前像 OpenClaw 这样的系统已经验证了 Skill 机制的可组合性，因此 Terrarium 完全可以借鉴这一思路，构建自己的“生命器官系统”。

当然，这种方案并不是唯一答案。Skills 只是其中一种有现实可行性的实现路径。它的意义在于提供一种较轻、较灵活、较容易起步的工程方向：

> **先定义生命体需要哪些能力，再把这些能力逐步实现为可调用、可组合、可演化的 Skills。**

从这个角度看，Skills 不只是工具集合，也可以被视为 Terrarium 的“认知器官”与“行为器官”。

---

## 七、结语

Terrarium 所代表的，并不是一次普通的“AI 开发提效”尝试，而是一种新的软件观：

> **未来的软件，可能不只是被开发出来的，而是能够在一定边界内自己成长出来的。**

这并不意味着完全放弃人的作用。相反，人仍然负责设定初始愿景、价值方向与边界条件；但项目本身将逐步获得更强的自我感知、自我调整、自我迭代能力。

如果这一方向成立，那么“AI 辅助开发”将只是过渡阶段；更深层的未来，也许是：

> **软件拥有自己的认知核心，并在 Terrarium 这样的环境中，像生命体一样持续演化。**
